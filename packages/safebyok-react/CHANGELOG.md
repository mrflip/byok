### Minor Changes

- [#115](https://github.com/mrflip/safebyok/pull/115) [`d5fa9b7`](https://github.com/mrflip/safebyok/commit/d5fa9b73d50053edb4b684b967a1da5996940db2) Thanks [@mrflip](https://github.com/mrflip)! - The passphrase dialog and the passkey button no longer throw to the host's error boundary. A failure that is not the user's to mend -- misuse, such as a closed vault handle, an `rpId` that does not fit the page or a vault made with a key deriver this build lacks, or a failure that is no `VaultError` -- was thrown while rendering, so the host's boundary replaced whatever it wrapped (often the whole app), or with no boundary the page went blank, and `withUnlockedVault` never settled. Now `PassphraseModal` shows a calm "Something went wrong" in place of its form, whose Close calls `onDone(false)`, so `withUnlockedVault` resolves null; `PasskeyUnlockButton` takes itself away and hands `onGripe` a word pointing the user to the passphrase. Each catches the error in a boundary of its own, so React reports it through the root's `onCaughtError` (the console, by default): hook an error tracker there to hear it. A `reentryHours` of no hours is met the same way. Conditions behave as before, and `VaultProvider`'s open still throws its misuse to the host's boundary at mount.
  
  `withUnlockedVault` now settles every call. Calls that overlap wait on one dialog and share its outcome, where the second used to replace the first, whose promise never settled. A dialog open when the provider unmounts, the user signs out or switches, or the vault reopens closes, and its calls resolve `null`; before, it hung, or came back over the next user's vault still holding the old user's action. An unlock that finishes after Cancel no longer closes a newer dialog. The dialog's gripe is announced to screen readers (`role="alert"`); the passkey button's word stays until the next submit, and focus moves to the passphrase field when the button goes. The trouble notice is an `alertdialog`, and Escape closes it.

A vault always keeps one passphrase: `removeUnlock` refuses removing the last with `last_unlock`, though passkeys remain. The snapshot's `unlocks` lists a passkey's `credential_id` and `prf_salt_b64` too (`UnlockSummary` is now a union by `method`). - [#44](https://github.com/mrflip/safebyok/pull/44) [`5ee702c`](https://github.com/mrflip/safebyok/commit/5ee702cda4c2d85abce7430b7da60dc9a58d6598) Thanks [@mrflip](https://github.com/mrflip)! - **Breaking:** `openVault`'s `keyDeriver` is required, and so is `VaultProvider`'s: `openVault` no longer falls back to the Argon2id deriver, so a bundled app that never imports it never ships it. An `openVault` without a `keyDeriver` refuses with kind `bad_option`. Vaults already stored read as before. **Also renamed, before the first release makes them costly:** the snapshot's `expiresAt` is now `askPassphraseAt`; the `openVault` and `VaultProvider` option `rememberForMs` is now `forcePassphraseReentryHours`, counted in hours (fractions allowed: `0.25` is fifteen minutes) and refused with kind `bad_option` unless above zero; and the exported `SevenDaysMs` is replaced by `ForcePassphraseReentryHours`, its default, 168. A host passing `rememberForMs: ms` passes `forcePassphraseReentryHours: ms / 3_600_000`. Remembered unlocks already on a device keep their deadline.

- [#44](https://github.com/mrflip/safebyok/pull/44) [`64d09c3`](https://github.com/mrflip/safebyok/commit/64d09c36dfc5c63f1781dea17c42354c244ccf3d) Thanks [@mrflip](https://github.com/mrflip)! - A vault holds at most 100 lockboxes by default (`MaxLockboxes`), raised with the new `openVault` option `maxLockboxes`; `store()` of a new lockbox in a full vault refuses with the new error kind `vault_full` (replacing a lockbox never does), and `VaultProvider` passes `maxLockboxes` through. **Breaking, for adapter authors:** `VaultDB` gains an abstract `maxVaultBytes`, the most the backend holds of one vault in bytes (`Infinity` for none), and `openVault` refuses with kind `bad_option` a `maxLockboxes` and `maxWhisperBytes` that might not fit it, or an adapter that does not declare it. A custom adapter adds `readonly maxVaultBytes = Infinity`, or its backend's real limit. A host that switches on every `VaultErrorKind` adds a case for `vault_full`. Vaults already stored read as before, and a vault already holding more than its limit keeps every lockbox: it can read, replace and erase them, and stores a new one once it is back under the limit.
