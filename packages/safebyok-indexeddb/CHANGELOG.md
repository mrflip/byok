# safebyok-indexeddb

## 0.4.0

### Minor Changes

- [#125](https://github.com/mrflip/safebyok/pull/125) [`80673f9`](https://github.com/mrflip/safebyok/commit/80673f9d073f592b111a9144df1a3eb26e394e6c) Thanks [@mrflip](https://github.com/mrflip)! - **Every adapter now compares a lockbox write's `vault_key_epoch`** (VAULTDB.md line 3.8): `idbVaultDB` in the write's transaction, the Convex component's `updateBox` mutation, and `postgresVaultDB` in the write's one statement, reading the vault's bundle row `FOR SHARE`; `graphqlVaultDB` gets it from the VaultDB its server serves. A lockbox write sealed under a vaultKey the bundle no longer stands for now refuses as `stale_write`, writing nothing. Every vault is at `vault_key_epoch` 1 today, so no write a host makes now is refused by it. Convex hosts redeploy the component to take it up.
  
  **Postgres: a bundle update waits for lockbox writes in flight.** The `FOR SHARE` read is a shared lock: lockbox writes never wait for each other on the bundle (two writes to one boxlabel still meet at its row, as before). If you installed the README's optional hard-cap trigger, replace it with the README's new version, which serializes inserts on an advisory lock: the old one's `FOR UPDATE` on the bundle row deadlocks two first writes into one vault, one of them failing as `storage_unavailable`.
  
  **`safebyok/testing`: `describeVaultDB` no longer takes `comparesVaultKeyEpoch`.** Line 3.8's tests run for every adapter; drop the option, and compare the epoch in your adapter's lockbox write.
  
  **`close()`, and a refresh that outlives the key, now stop a read in flight.** A `read()` or `use()` under way when the handle is closed hands back nothing and refuses with `vault_closed`; one under way when a refresh finds the vault's ways in changed on another device, or the vault gone, refuses with `vault_locked`. A `lockSoon()` grace running out, and a clock that cannot be read, still let a read in hand finish.
  
  **A device-store failure says what failed.** Still kind `storage_unavailable`, the device store's error its cause, but the message now names the step -- reading or writing the remembered unlock, reading or writing this device's mark of the vault, erasing either -- and what to do. `eraseDamagedVault` now reports a device-store failure the same way (it threw the device store's own error before).

- [#125](https://github.com/mrflip/safebyok/pull/125) [`6f037b4`](https://github.com/mrflip/safebyok/commit/6f037b43bcf3c7041280b6fa9966551ec85227f7) Thanks [@mrflip](https://github.com/mrflip)! - Names are held to a floor, the key-value stores join their ckeys on `^`, and the `VaultDB` verbs take no validators.
  
  - **A vault kept in `localVaultDB` or `idbVaultDB` before this release reads as absent** (its rows, filed under the old JSON-tuple ckeys, are left as they were), and a remembered unlock or device mark in `idbDeviceDB` is swept: the user unlocks, or makes the vault, again. Rows are now filed under `kind^applabel^user_id^vaultlabel[^boxlabel]` (`Ckeys`, whose functions are as before, with `Ckeys.Delimiter`).
  - **Every `VaultDB` verb loses its trailing `validators` argument.** A server or wrapper calling them drops it. Each verb holds every name to the floor and to a fact every adapter now declares, `maxNameBytes` (VAULTDB.md 7.3): an adapter of your own adds it. Postgres declares 640 bytes, and the GraphQL client the same.
  - **The floor** (`NameFloor`, `NoteFloor`, exported with `NameFloorBytes` and `NoteFloorBytes`): every name is one character to 1 KiB of UTF-8, every note at most 4 KiB, each well-formed Unicode in NFC with no control character (a note may hold tab and newline), and no name holds `^`, which the key-value stores join names on, whatever validators a host passes and whatever store holds the vault. A stored record below it reads back as damaged. `AnyTextValidators` is now the floor itself, so it refuses an empty name, a control character, a `^` or text not in NFC, as it did not before. A host on Convex, Postgres or GraphQL whose names hold `^` meets `bad_label` at `openVault`: there is no option to join on another character.
  - **A host's validators run at the vault's entry only**: a lockbox stored under a name or note they refuse now lists, reads and erases as sound, where it listed as damaged.
  - **`UserId`'s default is 1 to 100 ASCII letters, digits and `-_.:@+|`** (`UserIdPattern`), refusing spaces, other punctuation and text outside ASCII it used to admit: a host whose ids hold more passes its own `validators.userId`.
  - `listBoxes` sorts by code unit, never by the runtime's locale.

- [#125](https://github.com/mrflip/safebyok/pull/125) [`0b99b51`](https://github.com/mrflip/safebyok/commit/0b99b517f71318718d87e2d459dc5090f5d2674c) Thanks [@mrflip](https://github.com/mrflip)! - **Every storage adapter takes one bag of options, a `logger` among them.** `localVaultDB(store)` is now `localVaultDB({ store, logger })`, `convexVaultDB(client, api)` is `convexVaultDB({ client, api, logger })`, and `graphqlVaultDB(client, { maxLockboxes })` is `graphqlVaultDB({ client, maxLockboxes, logger })`; `idbVaultDB` and `postgresVaultDB` take `logger` in the bags they had. A VaultDB made with no logger uses the one `openVault` was given (`VaultDB.adoptLogger`), else the console. A VaultDB of your own takes `VaultDBOpts` and hands them to `super(opts)`.
  
  **`subscribe` guards its listeners.** A listener that throws, or returns a promise that rejects, no longer escapes into a write or the adapter: it is logged as an `error` (story `{ call: 'subscribe' }`) and handed to `reportError` where the platform has one, and every other listener is still called. An unsubscribed listener is never called again, and a second unsubscribe does nothing.
  
  **`VaultDB.listBoxRecords` is on every VaultDB**, so any VaultDB can be served over GraphQL: `safebyok-graphql`'s `ServedVaultDB` is any VaultDB, and `safebyok-postgres` no longer exports the `PostgresVaultDB` type (write `VaultDB`).
  
  **New exports from `safebyok`**: `Refusals` (the refusals an adapter throws, each cause never null), `Expectations` (the comparisons a key-value adapter makes), and the types `VaultDBOpts`, `LocalVaultDBOpts`, `WatchTrouble`; from `safebyok/idb`, `ChangeBell`, which `idbDeviceDB` now rings as `safebyok-indexeddb` does: other tabs hear a write even when this tab has no listener, and each listener runs on its own microtask.
  
  **Postgres and GraphQL set no lockbox limit by default** (`maxLockboxes` was 1000, now `Infinity`). A Postgres vault with no limit is never counted. Pass `maxLockboxes` to both, as before, to keep a limit.
  
  **Postgres logs a `listen` that fails to start; GraphQL logs a subscription that fails and calls `onChange`**, so the vault reads again and meets the refusal itself. Convex logs a `ConvexClient` watch that fails. A GraphQL validation error (`BAD_USER_INPUT`, `GRAPHQL_VALIDATION_FAILED`) now refuses as `bad_option`, not `storage_unavailable`. safebyok's own Convex refusals (`identity_revoked`, `vault_full`) no longer carry the `ConvexError` as their cause.
  
  **A GraphQL `vaultDBFor` that throws crosses as `bad_option` with a generic message**, saying the server's setup is wrong; its own message, which used to reach the browser, stays on the server as the GraphQL error's `cause`.
  
  **The Convex component's `updateBundle` lands only a bundle that keeps the vault's `vault_id` and moves its `unlock_epoch` forward**, else resolves `false` (`stale_write` to the client). Every safebyok client already writes so; a client that does not is refused.
  
  **An IndexedDB failure the browser gives no error for** reaches a caller as `storage_unavailable` whose cause reads "The storage backend failed without giving an error.", where it read "The IndexedDB request failed for an unknown reason".

- [#125](https://github.com/mrflip/safebyok/pull/125) [`91afb90`](https://github.com/mrflip/safebyok/commit/91afb90fe9a075dfb753204b141e16acb6ad92b4) Thanks [@mrflip](https://github.com/mrflip)! - **More lockboxes fit under a backend's vault limit.** `openVault` now plans 1 KiB, not 2 KiB, for each lockbox's fields beside its whisper and public bag when it checks that `maxLockboxes` lockboxes fit the adapter's `maxVaultBytes`. On Convex's 8 MiB, the default `maxWhisperBytes` admits 102 lockboxes (was 101), and a `maxWhisperBytes` of 2048 admits 1638 (was 1365). Nothing stored changes; a `maxLockboxes` that opened before still opens.
  
  **`store()` refuses an option it does not know** with kind `bad_option`, writing nothing: its only option is `public`, so a misspelt one, or a `note` left beside it from before the public bag, no longer passes unnoticed. Put a note in the bag: `store(boxlabel, whisper, { public: { note } })`.
  
  **The passphrase dialog's hidden username field stays hidden under a host's CSS**: it carries an inline `display: none` beside `hidden`, so a stylesheet rule such as `input { display: block }` no longer shows it.
  
  **`inspectIdbDeviceDB`'s `rows()` and `wipe()` refuse in a context with no IndexedDB** with a `NotSupportedError`, as `idbDeviceDB` does, and in a runtime with no `DOMException` (React Native's Hermes) that refusal is a plain `Error` of the same name, which a vault still says as `storage_blocked`.
  
  **A `storage_blocked` refusal keeps the verb's own way forward**: a remembered unlock this device cannot read now says to unlock with a passphrase or passkey instead, as its `storage_unavailable` refusal did.
  
  **`VaultProvider`'s default passphrase advice outlasts a strength test that fails to answer**: a rejected call (a zxcvbn chunk failing to load mid-typing, say) shows no advice rather than ending the dialog at the error boundary; Create runs the test again and says its refusal there.

The core always sends the standing `unlock_epoch` plus one, so no host's own writes change. VAULTDB.md (line 3.2) says a server-side adapter enforces it.
  
  **`idbVaultDB` refuses storage the browser withholds as `storage_blocked`**, not `storage_unavailable`: a `SecurityError`, `QuotaExceededError` or `NotSupportedError` from IndexedDB, or no IndexedDB at all, by the same rule the vault says its device store's failures by. A host that offered Retry on every `storage_unavailable` from this adapter now meets `storage_blocked` for these, which a retry cannot mend. The rule is exported for any adapter over the browser's own storage: `Refusals.isStorageBlocked(err)`, with `Refusals.storageBlocked(message?, opts?)` to refuse so.
  
  **`zxcvbnPassphraseTest` refuses a failed load with kind `storage_unavailable`**, not the bare error of a dynamic `import()`: a vault's Create, `addPassphrase` or `changePassphrase` whose word list could not be fetched now meets a condition a retry may mend, shown in place, and the failed load is its `cause`. Nothing of the passphrase is in either.

- [#79](https://github.com/mrflip/safebyok/pull/79) [`648b2c4`](https://github.com/mrflip/safebyok/commit/648b2c4fe365bf40bb115b34c57b1d5976524431) Thanks [@mrflip](https://github.com/mrflip)! - **`passphrase_epoch` is now `unlock_epoch`, in every stored record and every adapter, with no alias and no migration.** The counter moves whenever any way into the vault changes (a passphrase or a passkey added, removed or changed), so the old name no longer fit. It is renamed in the vault bundle (`VaultBundle`), the remembered device unlock (`DeviceUnlock`), a `VaultDB`'s `BundleExpectation`, `safebyok/testing`'s `bundleOf`, `safebyok-convex`'s tables and validators, `safebyok-indexeddb`'s checks, `safebyok-postgres`'s column (`vault-tables.sql` and the exported DDL), and `safebyok-graphql`'s schema fields. What a host with vaults already stored will see, by store:
  
  * **IndexedDB, `localVaultDB`, or a host's own `VaultDB`**: a bundle written under the old name fails validation and reads as `corrupt_record`, left as it is: a development vault is cleared from storage and made anew.
  * **Postgres**: `vault-tables.sql` creates only the tables that are missing, so running it again leaves an existing `safebyok_bundles` with its old column, and every bundle read and write fails as `storage_unavailable`, so no vault opens, until the host renames it, `ALTER TABLE safebyok_bundles RENAME COLUMN passphrase_epoch TO unlock_epoch` (which keeps every vault readable), or drops and re-creates the table.
  * **Convex**: a deployment holding bundle rows under the old name refuses the new component schema at deploy until those rows (and their vaults' lockboxes) are deleted.
  * **GraphQL**: the client and server halves must be the same version; a client of one against a server of the other fails every vault call as `storage_unavailable`.
  
  On every device, a remembered unlock written under the old name reads as absent, so that device asks for the passphrase once.

- [#79](https://github.com/mrflip/safebyok/pull/79) [`d6d278a`](https://github.com/mrflip/safebyok/commit/d6d278a939454b4139c91456ba3e54a263e7922e) Thanks [@mrflip](https://github.com/mrflip)! - **The IndexedDB vault store is a package of its own, `safebyok-indexeddb`; `safebyok/idb` keeps the device store.** A host using `idbVaultDB` changes one import, `from 'safebyok/idb'` to `from 'safebyok-indexeddb'`, and adds the package: its vaults read on unchanged, from the same IndexedDB database, rows and ckeys. `safebyok/idb` no longer exports `idbVaultDB` (no re-export is kept), and its `inspectIdb({ dbName, shelf })` becomes two windows, one beside each store: `inspectIdbDeviceDB({ dbName })` in `safebyok/idb`, and `inspectIdbVaultDB({ dbName })` in `safebyok-indexeddb`; the `IdbShelf` type is gone. Every verb of the new `idbVaultDB` is one IndexedDB transaction, where the old one read and wrote in two: a write racing another tab's now lands only while what it expects still stands, and is refused `stale_write` otherwise, two tabs creating a vault at once settle on one, and erasing a vault removes its every lockbox or none. A write now also tells other tabs over the BroadcastChannel when nothing in its own tab is listening, and a subscriber that throws no longer turns a write that landed into a refusal. Its README is the template for a key-value storage adapter of your own.

- [#79](https://github.com/mrflip/safebyok/pull/79) [`53b1f1a`](https://github.com/mrflip/safebyok/commit/53b1f1aabea16102dc7bfb6187410369e05b2e53) Thanks [@mrflip](https://github.com/mrflip)! - **Every storage adapter declares how many lockboxes it holds in one vault, and the Postgres server enforces its own.**
  
  * **Breaking, for adapter authors:** `VaultDB` gains an abstract `maxLockboxes`, the most lockboxes the backend holds in one vault, or `Infinity` for no limit. A custom adapter adds `readonly maxLockboxes = Infinity`, or its backend's real limit (a large whole number where the limit must cross a wire or be stored). `openVault` refuses, with kind `bad_option`, an adapter that declares none.
  * `openVault`'s `maxLockboxes` defaults to the smaller of `MaxLockboxes` (100) and the adapter's own, and is refused with kind `bad_option` when it is larger than the adapter's.
  * `localVaultDB` and `idbVaultDB` declare `Infinity`; `convexVaultDB` declares the component's own limit, 8,000.
  * `postgresVaultDB` takes a `maxLockboxes` option (default 1000; for no practical limit pass a large number, such as `1_200_300_400_500_600`, since `Infinity` cannot reach Postgres) and enforces it, as a best effort, inside the statement that inserts a new lockbox, refusing one past it with kind `vault_full`; a replacement never is. Writers racing for the last places may each find room and all land, a few past the limit, which the VaultDB contract allows. It keeps no count in the tables: `safebyok_bundles` has no `lockbox_count` column and nothing counts lockboxes by trigger.
  * `graphqlVaultDB(client, { maxLockboxes })` declares what the server's VaultDB enforces (default 1000, the Postgres VaultDB's default); the server's `vault_full` crosses as itself.

- [#90](https://github.com/mrflip/safebyok/pull/90) [`4988661`](https://github.com/mrflip/safebyok/commit/49886618f5fed0cdd41d00992bb0897dcdccf014) Thanks [@mrflip](https://github.com/mrflip)! - **The stored format changes, with no migration** (until 1.0.0, nothing binds backward). `localVaultDB`, safebyok-indexeddb's `idbVaultDB`, `idbDeviceDB` and `memoryDeviceDB` now file each row under the JSON text of its kind and names -- `["vault","acme","u1","main"]`, `["box","acme","u1","main","anthropic"]`, `["unlock","acme","u1","main"]` -- in place of the colon-joined `vault:acme:u1:main`. JSON quotes every name, so a name may hold any text, colons included, without two vaults ever sharing a row or listing each other's lockboxes.
  
  What a host will see: a vault stored by an earlier version under one of these adapters reads as absent, so `openVault` reports it `absent` and the next `unlock()` makes a new, empty vault; a remembered unlock reads as absent, so the user enters the passphrase again. Old vault rows are not read, moved or deleted; they hold only ciphertext, and a host that wants them gone wipes the vault shelf once (`inspectIdbVaultDB({ dbName }).wipe()` from safebyok-indexeddb, or the `localStorage` prefix it gave `domStore`). An old remembered unlock on the device is different, since it keeps the vaultKey wrapped under this browser's localUnlockKey: `idbDeviceDB` deletes it, unread, the first time it reads or erases a remembered unlock after the upgrade -- an open that finds the vault, or any lock; under `idbVaultDB` or `localVaultDB`, whose first open finds no vault, that is the first lock or the first open after an unlock -- along with any other row on the device shelf that is not under an unlock's new ckey, so `lock()` still forgets every unlock on the device. `idbDeviceDB({ dbName }).eraseAll()` now clears the whole device shelf. The Convex adapter keeps its names in columns and is unaffected.
  
  New export: `Ckeys`, the ckeys these adapters use (`bundle`, `box`, `unlock`, `boxPrefix`, `isBoxIn`, `isUnlock`), for an adapter of your own over a key-value store.
