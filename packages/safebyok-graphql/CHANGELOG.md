### Minor Changes

- [#125](https://github.com/mrflip/safebyok/pull/125) [`80673f9`](https://github.com/mrflip/safebyok/commit/80673f9d073f592b111a9144df1a3eb26e394e6c) Thanks [@mrflip](https://github.com/mrflip)! - **Every adapter now compares a lockbox write's `vault_key_epoch`** (VAULTDB.md line 3.8): `idbVaultDB` in the write's transaction, the Convex component's `updateBox` mutation, and `postgresVaultDB` in the write's one statement, reading the vault's bundle row `FOR SHARE`; `graphqlVaultDB` gets it from the VaultDB its server serves. A lockbox write sealed under a vaultKey the bundle no longer stands for now refuses as `stale_write`, writing nothing. Every vault is at `vault_key_epoch` 1 today, so no write a host makes now is refused by it. Convex hosts redeploy the component to take it up.
  
  **Postgres: a bundle update waits for lockbox writes in flight.** The `FOR SHARE` read is a shared lock: lockbox writes never wait for each other on the bundle (two writes to one boxlabel still meet at its row, as before). If you installed the README's optional hard-cap trigger, replace it with the README's new version, which serializes inserts on an advisory lock: the old one's `FOR UPDATE` on the bundle row deadlocks two first writes into one vault, one of them failing as `storage_unavailable`.
  
  **`safebyok/testing`: `describeVaultDB` no longer takes `comparesVaultKeyEpoch`.** Line 3.8's tests run for every adapter; drop the option, and compare the epoch in your adapter's lockbox write.
  
  **`close()`, and a refresh that outlives the key, now stop a read in flight.** A `read()` or `use()` under way when the handle is closed hands back nothing and refuses with `vault_closed`; one under way when a refresh finds the vault's ways in changed on another device, or the vault gone, refuses with `vault_locked`. A `lockSoon()` grace running out, and a clock that cannot be read, still let a read in hand finish.
  
  **A device-store failure says what failed.** Still kind `storage_unavailable`, the device store's error its cause, but the message now names the step -- reading or writing the remembered unlock, reading or writing this device's mark of the vault, erasing either -- and what to do. `eraseDamagedVault` now reports a device-store failure the same way (it threw the device store's own error before).

- [#125](https://github.com/mrflip/safebyok/pull/125) [`6f037b4`](https://github.com/mrflip/safebyok/commit/6f037b43bcf3c7041280b6fa9966551ec85227f7) Thanks [@mrflip](https://github.com/mrflip)! - Names are held to a floor, the key-value stores join their ckeys on `^`, and the `VaultDB` verbs take no validators.
  
  - **A vault kept in `localVaultDB` or `idbVaultDB` before this release reads as absent** (its rows, filed under the old JSON-tuple ckeys, are left as they were), and a remembered unlock or device mark in `idbDeviceDB` is swept: the user unlocks, or makes the vault, again. Rows are now filed under `kind^applabel^user_id^vaultlabel[^boxlabel]` (`Ckeys`, whose functions are as before, with `Ckeys.Delimiter`).
  - **Every `VaultDB` verb loses its trailing `validators` argument.** A server or wrapper calling them drops it. Each verb holds every name to the floor and to a fact every adapter now declares, `maxNameBytes` (VAULTDB.md 7.3): an adapter of your own adds it. Postgres declares 640 bytes, and the GraphQL client the same.
  - **The floor** (`NameFloor`, `NoteFloor`, exported with `NameFloorBytes` and `NoteFloorBytes`): every name is one character to 1 KiB of UTF-8, every note at most 4 KiB, each well-formed Unicode in NFC with no control character (a note may hold tab and newline), and no name holds `^`, which the key-value stores join names on, whatever validators a host passes and whatever store holds the vault. A stored record below it reads back as damaged. `AnyTextValidators` is now the floor itself, so it refuses an empty name, a control character, a `^` or text not in NFC, as it did not before. A host on Convex, Postgres or GraphQL whose names hold `^` meets `bad_label` at `openVault`: there is no option to join on another character.
  - **A host's validators run at the vault's entry only**: a lockbox stored under a name or note they refuse now lists, reads and erases as sound, where it listed as damaged.
  - **`UserId`'s default is 1 to 100 ASCII letters, digits and `-_.:@+|`** (`UserIdPattern`), refusing spaces, other punctuation and text outside ASCII it used to admit: a host whose ids hold more passes its own `validators.userId`.
  - `listBoxes` sorts by code unit, never by the runtime's locale.

- [#125](https://github.com/mrflip/safebyok/pull/125) [`443e7f6`](https://github.com/mrflip/safebyok/commit/443e7f68ab088fb290c62a37712c44d6bd67f18d) Thanks [@mrflip](https://github.com/mrflip)! - **Stored shape: a lockbox's note becomes a public bag of any JSON, and the lockbox reserves its whisper's codec and schema version.** The lockbox's format is `safebyok-lockbox-v3`. No lockbox written before this reads: no compatibility before 1.0. A `safebyok-lockbox-v2` lockbox lists as damaged (`{ boxlabel, damaged: true }`) and `read()` refuses it as `damaged_lockbox`; `erase()` it, or `store()` over it, which writes it afresh. The bundle, the unlock envelopes and the device records are unchanged, so a vault still opens and unlocks.
  
  - **`safebyok`**:
    - `store(boxlabel, whisper, { public })` takes the lockbox's **public bag**, any JSON value (`PublicBag`, exported), shown in the snapshot while locked as `box.public` and never interpreted by the vault. Left out, the lockbox keeps the bag it has, and a new lockbox gets `{}`; `{}` empties it. A bag JSON cannot carry is refused as `bad_option`. `opts.note` is gone: a host keeping a note moves it into the bag, as `{ public: { note } }`, and checks its bag's shape itself before `store()`.
    - The bag is stored as its JSON, keys sorted, in the lockbox's `public_json`, always written, and bound into both of the lockbox's encryptions with every other field of its header, so a bag altered or swapped in storage makes the lockbox refuse to open. The lockbox also records `whisper_codec` (`'json_v1'`) and `whisper_schema_version` (`1`), bound the same way. `LockboxSummary` carries `public` in place of `note`, and none of the three stored fields.
    - The stored `public_json` must be exactly the vault's own serialization (keys sorted, no spacing): a lockbox whose bag was respaced, reordered or nested too deep in storage lists as damaged. And a `store()` over a lockbox that will not decipher (its ciphertext, bag or times altered in storage) carries neither its bag nor its `registered_at` forward: the bag becomes `{}` unless one is given, and `registered_at` is now.
    - `maxWhisperBytes` counts the whisper's JSON and the bag's together, so a whisper of exactly `maxWhisperBytes` no longer fits beside even the empty bag's two bytes. A replacement is never refused as `vault_full` any more: it weighs what it replaces.
    - The note's checks go: `LockboxNote`, `MaxNoteChars`, `NoteFloor` and `NoteFloorBytes` are no longer exported, and `VaultValidators`, `DefaultValidators` and `AnyTextValidators` have no `note` field. A `validators` bag holding `note` is refused as `bad_option`, as any field the vault does not know is.
    - A lockbox's format is bound into its encryptions once, as the binding's leading tag, and no longer again inside its header.
  - **`safebyok-convex`**: the component's lockbox validator takes `safebyok-lockbox-v3` only, with `whisper_codec`, `whisper_schema_version` and `public_json` in place of `note`, so a deployment holding lockboxes written before this no longer matches its schema: delete the component's lockbox rows (or clear its tables) before deploying it.
  - **`safebyok-postgres`**: `safebyok_lockboxes` loses `note` and gains `whisper_codec` (text), `whisper_schema_version` (bigint) and `public_json` (text, never jsonb, which would rewrite the bound text), each `NOT NULL`. `VaultTablesSql` creates only missing tables, so drop and recreate a `safebyok_lockboxes` made before this.
  - **`safebyok-graphql`**: `SafebyokLockbox`, `SafebyokLockboxInput` and `SafebyokListedLockbox` lose `note` and gain `whisper_codec: String!`, `whisper_schema_version: Int!` and `public_json: String!`. A host serving the recipe's SDL deploys the new one with its server.
  - **`safebyok-react`**: `VaultProvider` passes no `note` check through, as there is none.

- [#79](https://github.com/mrflip/safebyok/pull/79) [`648b2c4`](https://github.com/mrflip/safebyok/commit/648b2c4fe365bf40bb115b34c57b1d5976524431) Thanks [@mrflip](https://github.com/mrflip)! - **`passphrase_epoch` is now `unlock_epoch`, in every stored record and every adapter, with no alias and no migration.** The counter moves whenever any way into the vault changes (a passphrase or a passkey added, removed or changed), so the old name no longer fit. It is renamed in the vault bundle (`VaultBundle`), the remembered device unlock (`DeviceUnlock`), a `VaultDB`'s `BundleExpectation`, `safebyok/testing`'s `bundleOf`, `safebyok-convex`'s tables and validators, `safebyok-indexeddb`'s checks, `safebyok-postgres`'s column (`vault-tables.sql` and the exported DDL), and `safebyok-graphql`'s schema fields. What a host with vaults already stored will see, by store:
  
  * **IndexedDB, `localVaultDB`, or a host's own `VaultDB`**: a bundle written under the old name fails validation and reads as `corrupt_record`, left as it is: a development vault is cleared from storage and made anew.
  * **Postgres**: `vault-tables.sql` creates only the tables that are missing, so running it again leaves an existing `safebyok_bundles` with its old column, and every bundle read and write fails as `storage_unavailable`, so no vault opens, until the host renames it, `ALTER TABLE safebyok_bundles RENAME COLUMN passphrase_epoch TO unlock_epoch` (which keeps every vault readable), or drops and re-creates the table.

  * **GraphQL**: the client and server halves must be the same version; a client of one against a server of the other fails every vault call as `storage_unavailable`.
  
  On every device, a remembered unlock written under the old name reads as absent, so that device asks for the passphrase once.

A custom adapter adds `readonly maxLockboxes = Infinity`, or its backend's real limit (a large whole number where the limit must cross a wire or be stored). `openVault` refuses, with kind `bad_option`, an adapter that declares none.

Its lockboxes list as damaged until then.
  
  - **`safebyok`**:
    - The bundle's format is `safebyok-vault-v2`. It gains `vault_key_epoch` (1 for a vault's first vaultKey) and `prior_vault_key` (absent until a vault's vaultKey is replaced). Each unlock envelope gains `vault_key_epoch`, `device_id` (a random id the device that added it keeps for the vault) and `registered_at`, all bound into its wrap. An envelope at another `vault_key_epoch` than its bundle's is passed over as damaged (`damaged_unlock`).
    - The lockbox's format is `safebyok-lockbox-v2`. It gains `vault_key_epoch`, bound into both its encryptions, so `LockboxSummary` and the snapshot's `boxes` carry it too. A lockbox at another epoch than its bundle's reads as `damaged_lockbox`.

An adapter of your own compares it in its `doUpdateBox`, beside `vault_id` and `revision_id`; `describeVaultDB` tests it, and its new option `comparesVaultKeyEpoch: false` holds that test pending for an adapter that does not yet. `localVaultDB` compares it; the IndexedDB, Convex and Postgres adapters (and GraphQL's recipe, over Postgres) do not yet. Nothing in this release replaces a vaultKey either, so every vault stands at epoch 1 and the comparison has nothing yet to refuse.
    - `DeviceDB` gains `readMark`, `writeMark` and `eraseMark`, which a host's own `DeviceDB` must implement (`openVault` refuses one without them as `bad_option`), and `eraseAll` erases marks too. A device mark (`DeviceMark`, format `safebyok-mark-v1`) holds the device's id for the vault and the highest `unlock_epoch` and `vault_key_epoch` it has seen. `memoryDeviceDB` and `idbDeviceDB` keep them; `Ckeys.mark` and `Ckeys.isMark` name their rows.

It is refused at open, unlock, every change to the ways in and every refresh, and nothing is taken from it. A host whose storage was restored from an older copy on purpose accepts it on a device by `deviceDB.eraseMark(scope)` and opening again (the README's *A vault rolled back*). `destroy()` and `eraseDamagedVault` erase the mark.
  - **`safebyok-convex`**: the component's validators carry the new fields and formats, so a deployment holding records written before this no longer matches its schema: clear the component's tables before deploying it.
  - **`safebyok-postgres`**: `safebyok_bundles` gains `vault_key_epoch` and `prior_vault_key`, and `safebyok_lockboxes` gains `vault_key_epoch`. `VaultTablesSql` creates only missing tables, so drop and recreate tables made before this.

  `safebyok_bundles` loses its `lockbox_count` column, and the count trigger, the `FOR UPDATE` row lock and the second read on a full vault go with it. A new lockbox is inserted in one statement that counts the vault's lockboxes as of its own start and says, from that one snapshot, why it missed: a vault at its limit is `vault_full`, a vault gone or a boxlabel already taken is `stale_write`, and so is a foreign key violation (`23503`) from a vault erased mid-statement. With no lock, writers racing for the last places under READ COMMITTED may each find room and all land, a few past the limit (by at most one less than the number of racers), which the contract allows (lines 4.2 to 4.5); the README says what it guarantees, that every guarantee holds at READ COMMITTED (above it some races fail with `40001`, refused as `storage_unavailable`), and offers an unsupported trigger for a host that wants a hard cap.

A host that wants other devices' writes pushed runs the new `VaultNotifySql` (also shipped as `vault-notify.sql`) once, and passes a `listen`; without it, `subscribe` never calls, the vault refreshes after its own writes, and another device's changes arrive on its next read. - [#120](https://github.com/mrflip/safebyok/pull/120) [`18a960b`](https://github.com/mrflip/safebyok/commit/18a960b5ff9d240643bf05e5a166d95d3a1d70fb) Thanks [@mrflip](https://github.com/mrflip)! - **`describeVaultDB` races its writers from two devices, under every interleaving it can make** (`safebyok/testing` grows). A new option, `makeDevices(turnstile)`, makes devices over one fresh backend -- each an adapter of its own, sharing nothing but the backend -- and passes the `turnstile` before each round trip a device makes to it (`throughTurnstile` wires one around a client's methods). The race lines (3.1 to 3.5, 3.7 and 4.5) then run under `raceEveryWay`: the moves made together, staggered a few microtasks and ticks each way round, and each move held before every one of its round trips while the other moves; four racers for the last place each held midway, then let go together. A device that cannot finish while another waits at the turnstile fails the race: the two share a lock, a queue or a connection that real devices would not, or the adapter holds a lock from one round trip to the next. `expectRoundTripsThroughTurnstile(makeDevices)` shows an adapter's factory wires it. Without `makeDevices`, the races run through one adapter as before, under the same schedules, and their titles say so.
  
  New checks across devices: line 2.1 (a write on one device seen by the next read on another), 4.5 past the limit (a vault filled by a device allowed more), and 6.1 from another device. The push tests no longer guess that a watch is live after 50 ms: they make a write the watch hears first, and then need some call to `onChange` to read the vault as each write left it, so a push that comes too early, or not at all, fails; an unsubscribed watch is checked through several writes, not one tick. Each of these checks is also exported, runnable on its own, as `vaultDBTimingChecks`.
  
  An adapter's own tests that pass `makeDevices` see new tests; one whose devices secretly share an adapter, a backend per device, or a lock now fails them.
  
  **`postgresVaultDB` calls a subscriber once as its listen begins** (`safebyok-postgres`). A write that landed while the listen was starting was never heard, and a vault -- which subscribes, then reads -- could read the vault before that write and show it stale until the next one. Now it reads again once the watch is live. Through it, **`safebyok-graphql`'s `safebyokVaultChanged` sends one change as the subscription starts**. A host counting `onChange` calls sees one more at the start; the VaultDB contract's line 6.1 now says a watch that starts late calls once it is live. The schema's description of `safebyokVaultChanged` reads "whenever the vault may have changed".
