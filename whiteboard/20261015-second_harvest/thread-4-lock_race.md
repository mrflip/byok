# Thread 4: lock_race (2026-10-15)

Branch `20261015-lock_race`, cut from [#53](https://github.com/mrflip/safebyok/pull/53)'s tip `544088d`; PR not yet filed, stacked on #53. Justify: green (root 105, safebyok 346, safebyok-convex 219, safebyok-react 16, demo 28); `pnpm size` within every limit.

* **Built**:
  - `vault.ts`: a per-handle counter, `shutsSoFar`, and `shut()`, the one path every lock takes (`lock()` and `destroy()` today): it moves the counter, nulls the vaultKey and `askPassphraseAt`, and erases the device record. `unlock()` and `changePassphrase()` note the counter when they start. `takeUpUnlock()` is now the one place a vaultKey is taken up: it checks the counter, writes the device record, checks again (erasing the record it just wrote if a shut landed meanwhile), and only then sets `vaultKey` and `askPassphraseAt`. `unlock()` also checks right after its opening look at storage, so a lock landing there spares the derivation and never makes an absent vault.
  - `settleUnlock()` hands back the bundle the passphrase was proven against (`standing`), and the device record binds to that, not to whatever bundle stands after the derivation. Needed so a `destroy()` landing mid-unlock is refused as `vault_locked` rather than as `absent_vault` from `currentBundle()`; it also binds the record to the bundle its key really came from.
  - `safebyok-react`'s `PassphraseModal`: on `vault_locked` from `unlock()` it calls `onDone(false)`, so `withUnlockedVault` resolves `null` (dismissed). It used to rethrow anything but `wrong_passphrase`, which would have left this rejection unhandled.
  - Tests: `tests/vault.test.ts`, *a lock that lands while an unlock is under way*, nine cases (each wait; already unlocked; a first unlock; a later unlock untouched; `destroy()`; `changePassphrase()` twice), all failing on the base. Each wait is held with `TH.makeGate()` (new, tested), armed by `makeRacingWorld()`'s `holdNext*`; the steerable clock reopens within the seven days. `passphrase-modal.test.tsx` gains the dismissal case.
  - Docs: the `Vault` doc blocks for `unlock`, `lock` and `changePassphrase`; the core README's *Locking*; a `notes/security.md` entry; `TODO.md` NOT YET gains the Coach's sentence (*A finer unlock race analyser*); `.changeset/20261015-lock_race.md` (patch, safebyok and safebyok-react).

* **Decisions taken**:
  - **A lost `unlock()` rejects, with kind `vault_locked`**, rather than resolving quietly. A resolve would tell the caller the vault opened when it did not (a host's "Unlocked!" toast would lie); `vault_locked` is the state the vault is really in, is a kind every host already handles, and matches `store()`, whose retry throws `vault_locked` when it finds the device relocked. No new error kind, so no surface change beyond the documented behaviour. The message names no secret.
  - **A vault the losing unlock was creating stays created** (locked, under that passphrase): the creation is a write to storage already made, and undoing it would be a delete racing other devices.
  - **The counter counts shuts, not unlocks.** A second unlock finishing does not defeat a first still under way: each takes up its own key, last one wins, as before.
  - **The bundle-moved race is not this thread's.** `refresh()`'s "outlived" path (the passphrase changed, or the vault was reborn, elsewhere) still just nulls the key; it does not go through `shut()` or move the counter, because an unlock's own opening refresh would then defeat it (a stale handle, the user typing the new passphrase). See *Discoveries*.

* **Deviations**:
  - **`changePassphrase()` does not abandon the change when a lock lands; it drops only the unlock.** The plan's gloss says it gives up "writing nothing more". Read literally, a lock landing during the ~1 s derivation would abandon the bundle write too, and the caller -- told nothing, or told `vault_locked` -- would believe one passphrase in force while the other is. The rulings (*Expiry*: "an operation already going is never clawed back ... in-flight work holding the key in a local still finishes") and the lowest-consequence rule both point to: the passphrase change lands (it was proven by the old passphrase, and works on a locked vault anyway), the device stays locked, and the call resolves. Its doc block says so.

* **Discoveries**:
  - **The lock wins within one handle only.** A `lock()` in one tab erases the device record, but an `unlock()` under way in another tab (another handle) does not see this handle's counter and will write the record afterwards. Noted in the security entry; a cross-tab answer needs a shared signal (BroadcastChannel, or a deviceDB generation), not in scope.
  - **The undoing erase is unconditional.** A losing unlock erases the device record after its own write; if a second unlock, begun after the lock on the same handle, wrote its record in between, that is erased too. The device then asks for the passphrase at its next open: the safe direction. DeviceDB has no compare-and-erase to do better.
  - **The bundle-moved race (pre-existing).** If the vault is destroyed and remade elsewhere while an unlock from `locked` is deriving, the change bell's refresh installs the new bundle (no key to null), and the unlock then takes up the old vault's key against it; a `store()` would seal under the old vaultKey into the new vault. The record now binds to the proven bundle (so it will not fit at the next open), but the in-memory key is still taken up. A fix: in `takeUpUnlock`, also refuse when `bundle`'s `vault_id`/`passphrase_epoch` no longer match `standing`'s (likely `stale_write`). Small, but a behaviour of its own; left for the Coach to place.
  - **For thread 5 (lockSoon)**: route the shut timer through `shut()` so an unlock under way loses to it too. `lockSoon()` itself, which closes the entry gate at once, probably wants to move the counter at call time (so an unlock already deriving loses), erase the record and set `askPassphraseAt` to now, leaving the timer only the key. Cancelling the pending shut is the opposite question ("has an unlock landed since?"), which the shut counter does not answer by design: clear the timer in `takeUpUnlock`, the one place a key is taken up, or have the timer compare `vaultKey` with the key it was set against.
