**How to read it.**

* Each entry is a plain summary. *Sources* lists every place it was raised; where several
  sources raised the same thing they are merged into one entry. Paths are `file:line` on
  `origin/main` unless a branch is named; `H:` is `human/`, `WB:` is `whiteboard/`. A PR link goes
  to the body; `rev` and `c` links go to the exact comment.
* Status is read against `origin/main` and the npm registry on 2026-10-15. *Addressed* means a
  merged PR, a commit, a Coach ruling, or (for low items) the author's recorded acceptance says it

### Cryptography and key handling

* **high** · A remembered unlock's `expires_at` is not bound into its encryption, so anyone who can
  write this device's IndexedDB can extend it. Clamping it to now + `forcePassphraseReentryHours`
  on read was proposed and not decided. A related point: a remembered unlock keeps the
  `expires_at` it was written with, even after a later open passes a shorter window. *Sources:*
  [#43][pr43]; `WB:20261015-low_hanging_fruit/thread-6-boundary_audit.md:67,76`;
  `notes/security.md:174`; [#40 rev][c40] "keeps the expires_at it was written with".
* **high** · Making the vaultKey non-extractable stops it being exported, not used: injected code
  (XSS, a malicious extension, an unlocked stolen device) can decrypt through the handle, and so
  read whispers, while the vault is unlocked. *Sources:* [#6][pr6];
  `WB:20261013-relic/proposed-README.md:144`.
* **high** · A superseded bundle kept in Convex's backups still opens the unrotated vaultKey with
  the old passphrase. *Sources:* [#8][pr8].
* **med** · Ciphertext length reveals whisper length. Padding is unbuilt, and it is undecided
  whether `maxWhisperBytes` measures the padded or the unpadded size, and which bucket watermarks
  to use. *Sources:* [#7][pr7]; [#8][pr8]; `TODO.md:298,305`.
* **med** · `forcePassphraseReentryHours` has no upper cap, so an absurd value pushes
  `askPassphraseAt` and the stored `expires_at` past `Number.MAX_SAFE_INTEGER` and past `Date`'s
  range. *Sources:* [#40][pr40]; [#40 rev][c40];
  `WB:20261015-low_hanging_fruit/thread-2-explicit_options.md:79,80`.
* **med** · The `keyDeriver` shape check accepts any positive `salt_bytes`, including 1 and values
  over the 65536 that `getRandomValues` allows. *Sources:* [#40 rev][c40].
* **med** · Locking stops new entries but does not revoke key handles already in use, so work
  holding the key finishes after a lock. *Sources:* `WB:20261014-crypto/rulings.md:84`.
* **med** · The ~560 ms per Argon2id derivation was measured only in V8, and never on browsers or
  mobile. *Sources:* `WB:20261013-relic/outline.md:39`; `H:20261014-crypto.md:16`.
* **med** · A hash-wasm KeyDeriver must carry the same label and the same hard-coded parameters,
  or vaults stop opening across devices. *Sources:* `TODO.md:220`.
* **med** · The demo calls Anthropic from the browser with `dangerouslyAllowBrowser`, and the
  provider receives the key on every request, so the user's spend caps are the real backstop.
  *Sources:* `H:20261014-foundations_round_two.md:21`;
  `WB:20261013-relic/proposed-README.md:132,146`.
* **med** · A `view` facility puts whispers into React state, which the README's advice does not
  mention. *Sources:* `WB:20261014-foundations/demo-interface-notes.md:54`.
* **low** · The unlock window is client-side politeness, so two devices can carry different
  windows. *Status:* unclear. *Sources:* `WB:20261014-crypto/rulings.md:98`.

### Concurrency and storage verbs

* **med** · A failed `openVault` leaks its storage subscription, which on Convex is a live watch,
  and each error-boundary reset repeats the leak. *Status:* still on main (`vault.ts:607`
  subscribes before the first `refresh()`, with no cleanup on a throw). The fix sits on the
  unpushed branch `20261015-open_vault_unsubscribe`, whose diff still uses pre-move paths.
  *Sources:* [#20][pr20]; [#20 rev][c20]; [#32][pr32];
  `H:20261015-sprint_convex_vaultdb_done.md:45`; `TODO.md:90`;
  `WB:20261014-convex_vaultdb/thread-4-convex_client.md:88`;
  `WB:20261014-convex_vaultdb/convex_vaultdb-progress.md:147`;
  `WB:20261014-low_hanging_fruit/20261014-low_hanging_fruit-preplan.md:11`;
  `WB:20261015-low_hanging_fruit/thread-3-provider_open_rejection.md:24,29`.
* **med** · IndexedDB's `versionedUpdate` is check-then-save across two transactions.
  `doEraseVault` lists and then deletes in two transactions, so a box another tab writes in
  between survives as an orphan, and orphaned lockboxes are no longer swept. idb-keyval's
  `update()` could make the bundle path atomic; `doUpdateBox` needs a two-key transaction.
  *Sources:* [#18][pr18]; [#18 rev a][c18a]; [#18 rev b][c18b];
  `WB:20261014-crypto/rulings.md:32`; `WB:20261014-convex_vaultdb/convex_vaultdb-plan.md:144`;
  `WB:20261014-convex_vaultdb/convex_vaultdb-progress.md:50`;
  `WB:20261014-convex_vaultdb/thread-2-storage_verbs.md:66,80`; `TODO.md:278`.
* **med** · The lockbox cap is a soft limit under concurrency. Two `store()`s on one handle, or
  rival devices filling the other slots, can each pass the count. *Sources:* [#34 rev][c34r];
  [#44][pr44]; `WB:20261015-low_hanging_fruit/thread-1-vault_size_cap.md:32`;
  `WB:20261015-low_hanging_fruit/thread-7-stale_write_retry.md:48`.
* **med** · The core's refreshes are not serialized: every open runs two at once, and they can
  interleave after a write. *Sources:* [#20 rev][c20];
  `WB:20261014-convex_vaultdb/convex_vaultdb-progress.md:147`.
* **med** · If the catch-up read after a stale refusal fails, `quietRefresh` swallows the error,
  so the device may not relock and the erase may not reach the snapshot. *Sources:*
  [#44 rev][c44].
* **med** · `store()` and `erase()` no longer look before writing, so a session made stale by a
  passphrase change elsewhere can write before it relocks, and `erase()` no longer stops it.
  *Sources:* `WB:20261014-convex_vaultdb/thread-2-storage_verbs.md:56`; [#18 rev b][c18b].
* **med** · `changePassphrase` and `destroy` are not retried, so a concurrent passphrase change
  can surface `stale_write` to the user. *Sources:*
  `WB:20261015-low_hanging_fruit/thread-7-stale_write_retry.md:28`.
* **med** · Convex calls have no timeout. Offline calls wait, and a write abandoned by a host's
  own timeout can still land when Convex resends it on reconnect. A failing watch is ignored
  (`onError` does nothing). *Sources:* [#20][pr20];
  `WB:20261014-convex_vaultdb/thread-4-convex_client.md:30,32`.
* **med** · The store backoff in open [#45][pr45] has had no review. It hand-rolls the jittered
  backoff instead of using p-retry or exponential-backoff, reverses thread 7's "no delay", adds a
  check beyond its brief, and can keep a spinner waiting about 6 s in the worst case. *Sources:*
  [#45][pr45]; `WB:20261015-low_hanging_fruit/thread-14-store_backoff.md:5,20,28,39,42` (on
  `20261015-store_backoff`); `WB:20261015-low_hanging_fruit/thread-7-stale_write_retry.md:21`.
* **low** · Targets with no conditional write (memory, localStorage) are treated as atomic because
  check-then-save is synchronous within one tab; across tabs it was never checked. *Status:*
  unclear. *Sources:* `WB:20261014-crypto/rulings.md:17`.
* **low** · `read()` and `use()` may report `corrupt_record` on a box that the successor vault
  rewrote: safe, but misleading. *Status:* unclear since #18. *Sources:* [#9][pr9].

### destroy() and erasing

* **high** · `destroy()` on a handle that never saw a bundle resolves without erasing, so "delete
  my account" can report success while a vault stands. *Sources:* [#18][pr18]; [#18 rev b][c18b];
  `H:20261015-sprint_convex_vaultdb_done.md:30`;
  `WB:20261014-convex_vaultdb/convex_vaultdb-progress.md:93`;
  `WB:20261014-convex_vaultdb/thread-2-storage_verbs.md:42,59,109`; `TODO.md:85`.
* **high** · After a refused `destroy()` the handle holds the successor's `vault_id`, so an app
  that retries automatically erases a vault made anew elsewhere. The reviewer asked for a line in
  the integration docs. *Sources:* [#18][pr18]; [#18 rev b][c18b];
  `H:20261015-sprint_convex_vaultdb_done.md:32`;
  `WB:20261014-convex_vaultdb/convex_vaultdb-progress.md:95`;
  `WB:20261014-convex_vaultdb/thread-2-storage_verbs.md:113`.
* **med** · A host's own retry loop around `stale_write` would store again a box erased on another
  device, bringing the erased secret back. *Sources:* [#44 rev][c44].
* **med** · `destroy()` deliberately needs no unlock, and is not guarded against a reborn vault,
  so an authenticated session alone can delete. *Status:* stated rationale; no ruling.
  *Sources:* `WB:20261013-relic/outline.md:110`; [#9][pr9] "`destroy()` stays deliberately
  unguarded".

### Vault size and Convex limits

* **high** · Nothing on the server caps a Convex vault. The client cap from #34 is the only thing
  keeping a vault small enough to erase in one transaction, so a modified client, or concurrent
  stores, can grow it past what `destroy()` can erase. The Coach said yes to a follow-up
  (`convex_server_cap`), and it is not filed. *Sources:* [#34][pr34]; [#34 c][c34c];
  `WB:20261015-low_hanging_fruit/thread-1-vault_size_cap.md:73`.
* **med** · Decisions in the size cap still await confirmation: the cap is in bytes rather than a
  lockbox count, the kind is named `vault_full`, and the fit check uses a share plus a 1 KiB
  allowance rather than the plan's product. (The Coach did answer that `maxVaultBytes` stays
  abstract.) *Sources:* [#34][pr34] "YOLO decisions for the Coach";
  `WB:20261015-low_hanging_fruit/thread-1-vault_size_cap.md:40,52,67`;
  `WB:20261014-low_hanging_fruit/20261014-low_hanging_fruit-preplan.md:242`.
* **med** · Every refresh reads every lockbox, so its cost grows with the vault, and one-shot
  WebCrypto holds a whole whisper in memory several times over. *Sources:*
  `WB:20261014-convex/design.md:85`.
* **low** · The 1 KiB per-lockbox allowance is smaller than a lockbox's other fields at their
  largest; it fits only because of the 0.5 share. *Sources:* [#34 rev][c34r].
* **low** · A vault at or over its limit does a full refresh on each refused store. *Sources:*
  [#34 rev][c34r].
* **low** · `localVaultDB`'s 1 MiB per-record ceiling is a choice, not a fact, and the local
  adapters' `Infinity` byte cap has no guard against browser quotas. *Sources:* [#7][pr7];
  `WB:20261014-low_hanging_fruit/20261014-low_hanging_fruit-preplan.md:54`.
* **low** · `watchVault` reads whole lockbox documents to emit revision pairs, because Convex
  cannot project fields. *Sources:* [#19 rev][c19];
  `WB:20261014-convex_vaultdb/convex_vaultdb-progress.md:131`.
